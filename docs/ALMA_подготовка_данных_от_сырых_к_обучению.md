# ALMA: подготовка данных от сырых рядов до обучения

Дата актуализации: 2026-05-20.

Этот документ фиксирует **текущий канонический путь данных** для размеченных
ALMA-датасетов и общего `paano_global`-кандидата. Старые логи экспериментов и
подтвержденные длинные доказательства удалены: оставлены только решения,
которые нужны для разработки и проверки.

## Scope

В активном scope:

- размеченные ALMA-датасеты `negermet`, `pritok`, `salt`;
- `norm_work` как экспертно подтвержденная чистая норма;
- сравнение `paano_shared` и production-candidate `paano_global`;
- domain decision layer для объяснения/фильтрации стартов.

Вне scope этого документа:

- Salym;
- test35 / `test_unlabeled_35`;
- экспертные пакеты для неразмеченных скважин;
- backend/API-интеграция.

## Текущий статус моделей

| Детектор | Роль | Статус |
|---|---|---|
| `paano_shared` | текущий production/default | остается default |
| `paano_global` | production-candidate | доказан benchmark, но не включен default |

`paano_global` не должен становиться default автоматически. Переключение default
должно быть отдельным решением после review.

## Канонический путь данных

```text
raw Excel / telemetry
-> регулярная временная сетка
-> per-well каналы
-> feature schema
-> reference-норма
-> balanced normal pool
-> PaAno encoder
-> score + onset
-> domain decision layer
```

## 1. Сырые ряды и единая частота

Подтверждено: внутри одной скважины разные каналы могут иметь разное количество
точек и собственную временную шкалу. Это нормальное свойство телеметрии.

Инженерная причина: датчики пишут новое значение при изменении, а если значение
не меняется, оно может повторяться реже. Поэтому плотность сырых точек не равна
качеству канала.

Решение:

- сырые каналы сравнивать по времени, покрытию и первому валидному значению;
- для общего encoder pool использовать одну физическую частоту;
- не смешивать разные частоты в одном global encoder, потому что один `patch`
  начнет означать разную физическую длительность;
- для `paano_global` используется единая сетка `5min`;
- текущие старые class-specific parquet-сетки допустимы только для
  `paano_shared`.

## 2. Пустые каналы

Подтверждено:

- all-NaN канал исключается из `raw_columns` конкретной скважины;
- скважина не выбрасывается целиком, если остальные каналы пригодны;
- общий shared set строится по доступным признакам после schema/reduction;
- полностью отсутствующий канал нельзя восстанавливать искусственно.

Решение:

- пустые каналы выкидывать;
- не дорисовывать синтетический канал;
- для global pipeline использовать fixed feature schema, чтобы `norm_work` не
  мог случайно схлопнуть feature reduction.

## 3. Пропуски и ресемплинг

Для текущей телеметрии default-интерполяция: **causal forward fill / zero-order
hold**.

Почему:

- данные событийные;
- измеренное значение физически считается актуальным до следующей записи;
- линейная/cubic/PCHIP/Kalman-интерполяция может дорисовать slope, которого не
  было;
- learned imputation типа SAITS/BRITS сейчас не нужна: пропусков мало, а риск
  синтетического тренда выше пользы.

Решение:

- базовый ресемплинг делать через forward fill;
- не использовать будущие точки для заполнения прошлого;
- learned imputation оставить только как отдельный research при тяжелых
  пропусках.

## 4. Coverage и история канала

Подтверждено по текущим production-датасетам: канал почти никогда не
выкидывается только из-за редкой сырой записи. Если канал появился рано, после
`ffill` он получает нормальную историю на регулярной сетке.

Решение:

- фильтр coverage оставить;
- sparse raw channel не считать плохим, если он появился рано и после `ffill`
  имеет нормальное покрытие;
- канал без достаточной ранней истории не использовать для обучения;
- в диагностике хранить причину исключения канала: all-NaN, низкое coverage,
  недостаточная история.

## 5. Нормальная зона

Инженерное решение: **весь период до `actual_start` считается нормальной
работой**. Искусственно сужать pre-anomaly участок нельзя, потому что
подозрительная зона должна входить в размеченный интервал аномалии.

Решение для размеченных скважин:

- default reference policy: `normal_windows`;
- нормальная зона: `timestamp < actual_start`;
- если интервалов несколько, брать норму до первого размеченного старта, пока
  нет отдельной логики multi-incident;
- не вырезать вручную "сомнительный хвост".

Решение для blind/unlabeled скважин:

- нельзя автоматически считать первые 20-40% ряда нормой;
- если нет разметки и внешне подтвержденной нормы, локальный reference не
  строится;
- безопасный статус: `Not assessed` / `unlabeled_no_reference`;
- для blind-инференса нужен population memory bank или внешний подтвержденный
  эталон нормы.

## 6. `norm_work`

`norm_work` - это экспертно подтвержденная нормальная работа на всем периоде.

Роль:

- нормальный донорский pool/guard;
- hard-negative проверка: детектор не должен массово срабатывать на чистой
  норме;
- источник нормальных эмбеддингов для будущих population experiments.

Ограничение:

- не смешивать `norm_work` старым способом, где он мог влиять на feature
  reduction;
- использовать через fixed schema и balanced sampling.

Дополнительно: скважины `305г`, `1996л`, `1995` экспертно описаны как
нормальное поведение при изменении частоты. Если соответствующие файлы есть в
активных данных и структура подтверждена, их можно рассматривать как кандидатов
на расширение `norm_work`.

## 7. Feature windows и patch size

Окна задаются в физическом времени, а не в "числе точек".

При общей сетке `5min`:

- короткие процессы покрываются короткими окнами;
- приток и соли требуют длинного контекста;
- `patch` должен иметь постоянный физический смысл внутри одного encoder.

Текущая сильная конфигурация для `paano_global`:

| Patch | Сетка | Физический контекст |
|---:|---:|---:|
| `192` | `5min` | 16 часов |
| `384` | `5min` | 32 часа |

Почему не одно окно: разные аномалии имеют разную скорость. `negermet` быстрый,
`pritok` и `salt` медленнее. Два масштаба дают модели короткий и длинный
контекст без каскада разных моделей.

## 8. Нормализация

Текущий принцип: robust/per-well нормализация относительно reference.

Решение:

- сравнивать скважину с её собственной нормой, когда честный reference есть;
- не давать near-constant каналам создавать гигантские искусственные z-score;
- для отчетов показывать физические значения каналов, а не только score;
- глобальную сопоставимость score решать через tail/conformal calibration, а не
  через отказ от per-well reference.

## 9. Режимные события

Режимное событие - это не обязательно авария.

Типовые режимные события:

- изменение выходной частоты;
- остановка/пуск;
- штатное изменение токов после смены частоты;
- перестройка давления после режима управления.

Решение:

- режимные события не смешивать с preprocessing;
- объяснять/фильтровать их в domain decision layer;
- candidate после regime event может быть подавлен или отправлен в review.

## 10. Калибровка score

Сырые score разных скважин и разных input contracts несопоставимы напрямую.

Решение:

- хранить `score_valid`;
- хранить `score_unavailable_reason`;
- хранить `input_contract`;
- coverage-aware метрики считать отдельно от обычного hit-rate;
- population memory bank нельзя сравнивать со старыми local-порогами без
  отдельного retune/calibration.

## 11. Domain rules по аномалиям

Экспертные правила полезны как **decision layer**, а не как простая добавка к
score.

Негерметичность НКТ:

- резкий рост давления на приеме;
- резкий рост температуры;
- колебания/изменение токов;
- процесс быстрый, step-like.

Приток:

- главный сигнал - тренд давления на приеме вверх или вниз;
- выходная частота является контрольным параметром;
- если давление меняется при неизменной частоте, это сильный признак притока;
- если параллельно меняется частота, изменение давления может быть штатной
  режимной реакцией.

Солеотложение:

- ухудшение работы насоса;
- давление на приеме обычно растет после разворота тренда;
- важны сопутствующие токи/нагрузка/мощность/температуры/вибрации;
- важно смотреть не только медиану "до/после", а форму периода до
  `actual_start` и после него.

Решение:

```text
PaAno/global model:
    ищет подозрительные события

domain decision layer:
    принимает / подавляет / отправляет в review
    объясняет физику события
```

Подтверждено experiment/ablation: простое сложение
`score = PaAno + weight * physics_score` не улучшило метрики и может создавать
лишние старты. Поэтому экспертные правила не являются additive score-веткой в
production.

## 12. Короткие ряды, нулевой score и fallback

Проблема: старое поведение могло давать нулевой score, когда модель фактически
не смогла оценить ряд из-за нехватки точек/reference. Это silent failure.

Текущее решение:

- если оценка невозможна, статус должен быть `Not assessed`;
- нулевой score в таком случае не означает норму;
- `score_valid=False`;
- причина пишется в `score_unavailable_reason`;
- отчеты показывают warning.

Почему не cascade `long -> medium -> short`:

- разные patch sizes дают разные распределения score;
- ломается сопоставимость и conformal/tail calibration;
- появляются скачки на границах переключения.

Почему не reflective padding:

- зеркалирование может нарисовать физически ложный разворот тренда;
- для нефтяной телеметрии безопаснее edge/hold.

Текущий safe default для `paano_global`:

```text
input padding = edge_hold
memory bank = local
```

Важно:

- `edge_hold` применяется только к `paano_global`;
- `paano_shared` автоматически не менялся;
- `ALMA_PAANO_INPUT_PADDING=none` сохранен как negative control;
- `ALMA_GLOBAL_MEMORY_BANK_MODE=population_fallback` сохранен только как
  research/diagnostic режим.

Population memory bank:

- реализован как opt-in experiment;
- отдельной калибровкой проверен;
- production-польза не доказана;
- для `negermet` population fallback провалил короткие интервалы;
- default остается `local`.

## 13. Production-candidate `paano_global`

Текущая проверенная конфигурация:

```text
dataset frequency = 5min
patch_short = 192
patch_long = 384
input padding = edge_hold
memory bank = local
norm_work = включен как normal pool / guard
Salym = не используется
test35 = не используется
```

Последний подтвержденный benchmark:

| Аномалия | Интервалы | Hit-rate | FAR/day | Starts | Median delay | P90 delay |
|---|---:|---:|---:|---:|---:|---:|
| `negermet` | `5` | `5/5 = 1.000` | `0.000` | `5` | `0.05h` | `0.72h` |
| `pritok` | `24` | `24/24 = 1.000` | `0.000` | `55` | `1.60h` | `5.33h` |
| `salt` | `8` | `8/8 = 1.000` | `0.000` | `14` | `1.00h` | `12.07h` |

Domain guard summary:

```text
negermet:
  accept=5, uncertain=1
  blind ю-я 39-651 остается uncertain

pritok:
  accept=3, uncertain=35, reject=26
  hard-negative нормальные случаи не auto-accept

salt:
  accept=14, uncertain=7, reject=1
  frequency-transition guard работает
```

Вывод: `paano_global` можно держать production-candidate рядом с
`paano_shared`, но не делать default без отдельного решения.

## Что уже работает

### `pritok`

Текущая архитектура близка к правильной унифицированной форме:

```text
PaAno Shared core + pressure_trend branch + train-only tuning
```

Физическая ветка давления оправдана, потому что для притока главный ранний
сигнал действительно сосредоточен в давлении на приеме насоса. Текущая проблема
скорее в компромиссе раннее обнаружение / повторные старты, а не в ядре модели.

### `negermet`

`paano_shared` уже ловит все размеченные интервалы с практически нулевой
медианной задержкой. Для `negermet` физическая ветка нужна в первую очередь для
объяснимости и устойчивости, а не для срочного поднятия hit-rate.

Правильная физика для `negermet` - не только `pressure_drop`, потому что по
фактическим данным давление на приеме часто не падает, а резко растет. Более
корректная формулировка:

```text
leak_signature = pressure_step + load_response + thermal/vibration support
```

### `salt`

`salt/paano_shared` после добавления `salt_deposition`-ветки и расширенного
state-machine tuning выигрывает у старого `ensemble` по раннему старту и шуму:

- median delay: `0.033 h` против `3.192 h`;
- p90 delay ratio: `0.0667` против `0.5869`.
- FAR/day: `0.0156` против `0.0976`;
- starts/interval: `3.25` против `19.125`.

Главный вывод: проблему соли удалось решить без замены core-модели. Достаточно
было оставить `PaAno Shared + salt_deposition` и дать train-only tuning управлять
длинным re-arm/cooldown, чтобы одна длинная солевая аномалия не дробилась на
десятки повторных стартов.

5. После изменения прогнать `salt/paano_shared` на сервере через GPU - выполнено.

## Второе обязательное улучшение

### Обновить тесты под новую objective-функцию соли

Текущий тестовый долг:

```text
tests/test_generic_detection.py
test_operational_score_key_strongly_prefers_lower_start_count
```

Смысл старого теста: для соли сильно предпочитать меньшее число стартов.

Смысл новой системы: для соли сначала нужно удерживать hit-rate и ранний onset,
а затем снижать FAR и starts. Иначе модель формально “чистая”, но находит соль
слишком поздно.

Что нужно поменять:

1. Тест должен явно проверять, что `salt/paano_shared` предпочитает раннее
   обнаружение при приемлемом FAR.
2. Отдельный тест должен проверять, что экстремально шумная конфигурация все
   равно проигрывает при равной задержке.
3. Добавить регрессионный тест на `rearm_window_minutes`, чтобы длинные солевые
   интервалы не давали десятки повторных стартов.

## Улучшение средней уверенности

### Leave-one-well-out tuning для маленьких датасетов

Сейчас подбор конфигурации агрегирует train wells в общий summary. Для наших
малых выборок это может переобучаться на несколько легких скважин.

Более честный вариант:

```text
для каждой candidate-config:
  считать метрики по каждой train-скважине отдельно;
  оптимизировать не только общий средний score,
  но и устойчивость по held-out well / worst quantile;
```

Это особенно важно для:

- `salt`, где разные скважины имеют разную длину и разную длительность
  аномального интервала;
- `pritok`, где новый pressure trend может быть сильным на одних скважинах и
  слабым на других;
- `negermet`, где выборка маленькая и 5/5 легко переоценить.

Это улучшение выглядит правильным архитектурно, но его нужно внедрять после
фикса re-arm/cooldown, чтобы не смешивать две причины изменения метрик.

## Улучшение средней уверенности

### Calibrated tail / conformal-style score

У нас уже есть эмпирический tail-score относительно reference. Его можно
усилить и сделать более явным:

```text
raw score -> per-well reference distribution -> calibrated p-value/FAR score
```

Польза:

- score разных веток становится сопоставимым;
- fusion работает на calibrated scale, а не на случайных raw-величинах;
- отчеты честнее объясняют, что score означает.

Ограничение: reference-окна по некоторым скважинам короткие и шумные, поэтому
это нужно внедрять аккуратно и проверять на train-only tuning.

## Улучшение средней уверенности для `salt`

### Moving-window KS / distribution shift как диагностическая ветка

Для соли физика - это не один канал, а многомерный дрейф режима. Поэтому
перспективна дополнительная ветка:

```text
salt_distribution_shift_score =
  KS / non-parametric distance между reference residuals и текущим окном
```

Она должна работать не вместо текущего `salt_deposition_score`, а как
экспериментальная диагностическая ветка с train-only weight.

Причина: внешние источники по industrial process monitoring показывают, что
PCA/ICA + moving-window KS может снижать false alarms и missed detections в
многомерных технологических процессах.

## Что пока не стоит делать

### Не заменять PaAno на новую deep-модель

Внешний поиск показывает много современных MTSAD-подходов:

- transformer/autoencoder/reconstruction;
- GAN/MTAD-GAN;
- time-series foundation models.

Но по нашим текущим метрикам bottleneck не в core-модели:

- `negermet` уже 5/5;
- `pritok` работает физически согласованно;
- `salt` уже нашел ранний onset, но шумит re-arm/post-processing.

Замена core-модели сейчас даст больше риска, чем пользы.

### Не возвращать `salt ensemble` как финальную архитектуру

`ensemble` полезен как baseline и как источник идеи multivariate residual, но
он архитектурно хуже:

- отдельный детектор вместо единого `paano_shared`;
- хуже p90 delay ratio;
- содержит ручной fusion-alpha.

Правильный путь - не “вернуть ensemble”, а перенести его сильную часть внутрь
унифицированной архитектуры:

```text
PaAno Shared core + salt multivariate residual/tail physical branch
```

## Внешние источники

Использованы через Tavily на 2026-05-06.

1. Sensors 2025 survey по multivariate time-series anomaly detection:
   https://www.mdpi.com/1424-8220/25/1/190

   Вывод для нас: промышленные MTSAD-задачи требуют учитывать и временную
   зависимость, и связи между каналами. Это подтверждает архитектуру
   `PaAno + multichannel physical branch`.

2. IBM / ICLR 2026 adaptive conformal anomaly detection:
   https://research.ibm.com/publications/adaptive-conformal-anomaly-detection-with-time-series-foundation-models-for-signal-monitoring

   Вывод для нас: score желательно калибровать в интерпретируемую шкалу
   p-value / false-alarm-rate, особенно при distribution shift.

3. arXiv версия adaptive conformal anomaly detection:
   https://arxiv.org/html/2604.20122v1

   Вывод для нас: conformal/tail calibration можно делать post-hoc,
   не заменяя основную модель.

4. MDPI Processes 2024 PCA-KS для industrial process monitoring:
   https://www.mdpi.com/2305-7084/8/1/1

   Вывод для нас: для `salt` имеет смысл проверять moving-window
   distribution-shift statistic поверх PCA/SPE/residual, потому что соль
   выглядит как многомерный технологический drift.

5. Oil and gas multivariate time-series anomaly detection:
   https://www.mdpi.com/2076-3417/13/3/1891

   Вывод для нас: для нефтегазовой телеметрии нормальна гибридная логика,
   где модель реконструкции/аномальности сочетается с межканальными
   зависимостями и доменной физикой.

# Состояние пайплайна детекции на 13 марта 2026

## Контекст

Документ фиксирует итоговое состояние пайплайна после серии прогонов и нескольких итераций правок:

- перестроен единый blind-pipeline для `negermet`, `pritok`, `salt`
- оставлен только актуальный shortlist детекторов
- `TranAD` полностью убран из рабочего контура
- основным детектором во всех трёх задачах выбран `pca_spe`
- отчёты переведены на упрощённый русский формат для не-технических пользователей

Текущие выводы опираются на итоговые `benchmark_summary.json` после последнего стабильного прогона.

## Итог по детекторам

### Основной рабочий детектор

Для всех трёх аномалий текущим дефолтным детектором зафиксирован `pca_spe`.

Причины:

- он стабильно даёт лучший или сопоставимый `hit_rate`
- он понятнее и устойчивее, чем `fused`
- после серии прогонов он показал лучший суммарный баланс между полнотой, задержкой и ложными срабатываниями

### Альтернативы

- `fused` не дал устойчивого выигрыша и чаще ухудшал либо шум, либо задержку
- `lof` оставлен только как вспомогательный baseline для `negermet`
- `iforest` и `paano_feat` не являются текущими основными кандидатами

## Итог по аномалиям

### 1. Негерметичность НКТ (`negermet`)

Текущее состояние:

- детектор: `pca_spe`
- найдено: `5/5`
- train: `4/4`
- test: `1/1`
- `false_alarms_per_day`: `0.6875`
- `avg_starts_per_interval`: `3.6`
- `p90_abs_delay_hours`: `12.59`

Что улучшилось:

- после точечной правки mask/onset удалось поймать ранее проблемную скважину `1123л`
- тестовая `3509г` стабильно обнаруживается
- по полноте это сейчас лучший результат среди всех прогонов

Что остаётся проблемой:

- шум всё ещё высокий для production-режима
- повторных стартов на интервал всё ещё больше, чем хотелось бы

Практический вывод:

- по `negermet` текущий pipeline можно считать рабочим по полноте
- следующий шаг здесь уже не про recall, а про снижение лишних стартов

### 2. Изменение притока (`pritok`)

Текущее состояние:

- детектор: `pca_spe`
- найдено: `4/4`
- train: `2/2`
- test: `2/2`
- `false_alarms_per_day`: `0.1111`
- `avg_starts_per_interval`: `26.5`
- `p90_abs_delay_hours`: `85.85`

Что хорошо:

- полнота снова восстановлена до `4/4`
- тестовые скважины находятся
- по ложным срабатываниям на сутки картина лучше, чем в ранних версиях пайплайна

Что плохо:

- задержка на части скважин всё ещё большая
- число стартов на интервал слишком высокое
- особенно это заметно на test-части, где `avg_starts_per_interval = 40.0`

Практический вывод:

- `pritok` сейчас уже рабочий по факту обнаружения
- основная инженерная задача дальше: не искать новую модель, а ускорять onset и жёстче схлопывать повторные старты

### 3. Солеотложение (`salt`)

Текущее состояние:

- детектор: `pca_spe`
- найдено: `9/9`
- train: `8/8`
- test: `1/1`
- `false_alarms_per_day`: `0.3706`
- `avg_starts_per_interval`: `49.89`
- `p90_abs_delay_hours`: `70.45`

Что хорошо:

- полный `9/9`
- тестовая `2991г` находится
- по test-скважине задержка хорошая: `1.33 ч`

Что плохо:

- на train-части всё ещё много повторных стартов
- операционно отчёт и сигнализация всё ещё слишком шумные
- часть train-скважин детектится сильно позже оптимального момента

Практический вывод:

- по `salt` задача “поймать аномалию” решена
- нерешённой остаётся задача “сделать детекцию спокойной и ранней”

## Текущее лучшее решение

На текущем этапе в проекте зафиксировано следующее рабочее состояние:

- `negermet -> pca_spe`
- `pritok -> pca_spe`
- `salt -> pca_spe`

Это состояние не является идеальным, но на текущий момент оно лучше всех предыдущих итераций по суммарному компромиссу между:

- полнотой
- стабильностью
- интерпретируемостью
- воспроизводимостью

## Что уже сделано в коде

К моменту фиксации этого состояния в проекте уже реализовано:

- единый blind detection pipeline
- `Polars + Parquet + Calamine`
- `Optuna`
- `Plotly` для основного HTML-отчёта
- causal preprocessing без leakage от интерполяции
- raw-cache для Excel
- отказ от `TranAD` в рабочем контуре
- shortlist benchmark вместо полного тяжёлого прогона всех вариантов

## Что считать текущим ограничением

Главное ограничение сейчас уже не в моделях, а в operational-слое:

- слишком много повторных стартов
- поздние старты на части скважин
- избыточный шум в отчётах и итоговой сигнализации

Именно поэтому следующий этап должен быть не про “ещё одну новую модель”, а про:

- post-processing по эпизодам
- дедупликацию стартов
- более спокойный business-facing reporting

## Что делать дальше

Рекомендуемый следующий этап:

1. Не менять основной детектор.
2. Оставить `pca_spe` как дефолт для всех трёх аномалий.
3. Улучшать только operational-layer:
   - схлопывание повторных стартов
   - снижение `false_alarms_per_day`
   - ускорение onset на `pritok`
   - успокоение train-case'ов на `salt`
4. Отдельно улучшать пользовательские отчёты под инженеров и бизнес-пользователей.

Проект находится в рабочем состоянии.

Текущий результат:

- `negermet`: хороший по полноте
- `pritok`: хороший по полноте, средний по задержке
- `salt`: хороший по полноте, средний по шуму и train-задержкам

# ТЗ: подготовка сырого датасета Salym из Parquet и Excel

## 1. Цель

Подготовить отдельный сырой контур данных для Salym, не смешивая его с текущими рабочими датасетами и артефактами `paano`.

На этом этапе задача:

- извлечь из новой Salym БД только нужные динамические параметры;
- разложить данные по скважинам в отдельную структуру хранения;
- сохранить для каждого параметра исходную временную шкалу;
- собрать метаданные по скважинам и аномальным периодам из Excel;
- не выполнять интерполяцию, ресемплинг и приведение к общей временной сетке;
- не интегрировать результат в текущий production pipeline до отдельного решения.

## 2. Источники данных

### 2.1 Parquet-источник

Папка:

- `salym/parquet/`

Содержимое:

- `120` parquet-файлов;
- `30` уникальных параметров;
- `4` года: `2015`, `2016`, `2017`, `2018`;
- файлы именуются по шаблону `<parameter>_<year>.parquet`.

Общая схема parquet-файлов:

- `Tag`
- `TimeStampText`
- `TimeStamp`
- `ValueText`
- `Value`

Пример тега:

- `field1.wellpad01.well103.ESP.Frequency`

### 2.2 Excel-источник

Файл:

- `salym/сводная_информация_салим.xlsx`

Назначение на данном этапе:

- справочник скважин;
- эксплуатационные циклы;
- метаданные по ремонту и отказам;
- источник таблицы периодов аномалий/событий.

Excel не используется как источник raw-динамики.

## 3. Ограничения этапа

На текущем этапе запрещено:

- смешивать Salym-результаты с текущими файлами в `db/`;
- приводить данные к единой временной сетке;
- делать wide-таблицу на все скважины;
- интерполировать разрывы;
- заменять пропуски нулями;
- использовать Excel как замену telemetry;
- подстраивать формат результата под текущий `paano` раньше времени.

## 4. Параметры, которые нужно извлекать

Берутся только параметры, которые уже сопоставляются с текущим существующим датасетом.

Соответствие raw-тегов Salym и текущих параметров:

|---|---|

| `ESP.Frequency` | `Выходная частота` |
| `ESP.IntakePressure` | `Давление на приеме насоса кгс/см²` |
| `ESP.Motor.CurrentUnbalance` | `Дисбаланс токов` |
| `ESP.Motor.Load` | `Коэффициент загрузки ПЭД` |
| `ESP.Motor.VoltageAB` | `Линейное напряжение по фазе АB` |
| `ESP.Motor.VoltageBC` | `Линейное напряжение по фазе ВC` |
| `ESP.Motor.VoltageCA` | `Линейное напряжение по фазе СA` |
| `ESP.IntakeTemperature` | `Температура на приёме насоса` |
| `ESP.Motor.CurrentU` | `Ток на фазе А` |

- финальную верификацию физического смысла оставить на отдельный шаг.

## 5. Принцип хранения данных

### 5.1 Базовое решение

Raw-слой хранится в отдельной папке.

Структура:

```text
salym_prepared/
  metadata/
  anomalies/
  qc/
  raw_wells/
    <well_id_1>/
      ESP.Frequency.parquet
      ESP.IntakePressure.parquet
      ESP.Motor.Load.parquet
      ...
    <well_id_2>/
      ...
```

### 5.2 Единица хранения

На первом этапе:

- папка = одна скважина;
- файл parquet = один параметр одной скважины;
- у каждого параметра сохраняется собственная временная шкала.

### 5.3 Почему выбран именно такой формат

Этот формат обязателен, потому что:

- разные параметры имеют разную частоту и разную плотность наблюдений;
- насильственное приведение к одной сетке даст искусственные пропуски;
- wide-формат на данном этапе преждевременен;
- long-файл на всю скважину допустим, но дублирует `param_key` и хуже читается/обслуживается;
- отдельный parquet на параметр лучше отражает исходную природу данных.

Итог:

- разная длина рядов по параметрам внутри одной скважины допустима и считается корректной;
- отсутствие единой сетки на данном этапе не считается ошибкой.

## 6. Нормализация идентификаторов скважин

### 6.1 Извлечение из Tag

Из `Tag` извлекаются:

- `field_tag`
- `pad_tag`
- `well_tag`
- `param_tag`

Пример:

- `field1.wellpad01.well103.ESP.Frequency`

должен быть распарсен в:

- `field_tag = field1`
- `pad_tag = wellpad01`
- `well_tag = well103`
- `param_tag = ESP.Frequency`

### 6.2 Техническая нормализация

Дополнительно выделяются:

- `pad_num`
- `pad_suffix`
- `well_num`

Примеры:

- `wellpad01 -> pad_num=1, pad_suffix=NULL`
- `wellpad01A -> pad_num=1, pad_suffix=A`
- `well103 -> well_num=103`

### 6.3 Связь с Excel

Матчинг с Excel выполнять по:

- `pad_num`
- `pad_suffix`
- `well_num`

Не использовать прямой строковый join по исходному имени скважины.

## 7. Исключение неоднозначных скважин

Из обработки полностью исключаются скважины, для которых один и тот же числовой `Pad + Well` соответствует нескольким именам в Excel.

Список известных неоднозначных случаев:

- `K01 / 306` -> `US-306`, `US-306A`
- `K03 / 1532` -> `WS-1532`, `WS-1532ST1`
- `K06 / 8372` -> `US-8372`, `US-8372ST1`
- `K07 / 185` -> `US-185`, `US-185ST1`
- `K15 / 8327` -> `US-8327`, `US-8327ST1`
- `K54 / 1021` -> `SVA-1021`, `SVA-1021ST1`
- `K54 / 1059` -> `SVA-1059`, `SVA-1059ST2`
- `K56 / 51190` -> `SVA-51190`, `SVA-51190ST1`
- `K102 / 7085` -> `WS-7085`, `WS-7085ST1`
- `K114 / 7587` -> `WS-7587`, `WS-7587ST1`
- `K151 / 1082` -> `SVA-1082`, `SVA-1082ST1`

Отдельно сохранить список исключений в:

- `salym_prepared/metadata/excluded_ambiguous_wells.parquet`

## 8. Политика отбора скважин

Стартовый приоритет:

- использовать только скважины, которые присутствуют во всех 4 годах;
- в первую очередь ориентироваться на стабильное присутствие по `ESP.Frequency`;
- дальнейшее ужесточение пересечения по всем 15 параметрам оставить на отдельный QC-этап.

Уже подтверждено:

- по `ESP.Frequency` в `2015-2018` стабильно присутствуют `582` скважины.

Эта величина является рабочей консервативной нижней оценкой стартового пула до дополнительной фильтрации.

## 9. Политика обработки значений качества

### 9.1 Что запрещено

Запрещено:

- превращать `Bad` в `0`;
- превращать `-9999` в `0`;
- превращать `-32768` в `0`;
- делать физически недостоверное заполнение пропусков.

### 9.2 Что нужно сделать

Все специальные невалидные значения должны быть унифицированы в единый missing marker на уровне численного поля:

- `value = NULL/NaN`

При этом причина пропуска должна сохраняться отдельно.

Рекомендуемый набор флагов:

- `quality_flag = ok`
- `quality_flag = bad_text`
- `quality_flag = sentinel_-9999`
- `quality_flag = sentinel_-32768`
- `quality_flag = text_only`

Допускается внутреннее унифицированное представление:

- `value = NaN`
- `quality_group = missing_nonphysical`

но исходную причину желательно не терять.

### 9.3 Что пока не делать

На этом этапе не делать:

- проверку нулей через `Frequency`;
- интерполяцию;
- ресемплинг;
- восстановление пропусков.

## 10. Формат parquet-файла параметра скважины

Каждый parquet-файл одного параметра одной скважины должен содержать минимум такие колонки:

- `timestamp`
- `value`
- `value_text`
- `quality_flag`
- `source_tag`
- `source_year`

Рекомендуется дополнительно хранить:

- `well_id`
- `param_key`

Требования:

- `timestamp` хранится как timestamp-тип;
- строки из разных лет должны быть объединены в один файл по времени;
- сортировка внутри файла обязательна по `timestamp ASC`;
- дубликаты на одинаковом `timestamp` должны быть либо сохранены в исходном виде с отдельным флагом, либо детерминированно разрешены по отдельному правилу;
- на этом этапе не агрегировать и не усреднять точки.

## 13. Требования к производительности и реализации

Реализация должна быть рассчитана на объём порядка `67 GB` parquet-данных и не должна строиться как полное чтение всего набора в `pandas`.

Предпочтительный стек:

- `DuckDB` как основной движок массового чтения parquet;
- `Polars` как слой lazy/streaming обработки и записи parquet;
- `PyArrow` только для схемы, метаданных и точечных операций.

Обязательные требования:

- projection pushdown;
- filter pushdown;
- обработка только 15 нужных параметров;
- чтение только нужных колонок;
- запись результатов инкрементально;
- отсутствие единого гигантского in-memory DataFrame на весь Salym.

### 13.1 Фактическая реализация текущего этапа

В текущей реализации raw-этап собран отдельным модулем:

- `alma_service/salym_raw_pipeline.py`
- `scripts/salym/build_salym_raw.py`

Фактически использованный стек на этом этапе:

- `PyArrow ParquetFile.iter_batches(...)` для потокового чтения исходных parquet;
- `Polars` для записи итоговых parquet, compaction и QC;
- `pandas` только для Excel-реестра и отдельных служебных merge/groupby операций.

Примечание:

- `DuckDB` на уровне ТЗ остаётся желательным вариантом для следующей итерации оптимизации;
- текущий рабочий контур собран без `DuckDB`, но с batch-by-batch чтением и без единого полного in-memory чтения всех `67 GB`.

## 18. Подробное описание фактической обработки

### 18.1 Как проходит pipeline

Фактическая последовательность обработки следующая:

1. Из Excel читается реестр скважин и ремонтов.
2. Из `ESP.Frequency_2015..2018.parquet` строится таблица присутствия скважин по годам.
3. По `pad_num + pad_suffix + well_num` выполняется матчинг telemetry-скважин с Excel.
4. Из стартового пула отбираются скважины, которые:
   - присутствуют все 4 года по `ESP.Frequency`;
   - не попали в ambiguous cases;
   - имеют успешный match с Excel.
5. Для каждого из `15` параметров и каждого года читаются только колонки:
   - `Tag`
   - `TimeStamp`
   - `ValueText`
   - `Value`
6. Каждая batch-порция раскладывается по выбранным скважинам в промежуточные fragment-файлы.
7. На стадии compaction fragment-файлы склеиваются в финальные:
   - `raw_wells/<well_id>/<param_key>.parquet`
8. Отдельно строится QC-таблица покрытия.
9. Отдельно из Excel строятся:
   - `equipment_cycles.parquet`
   - `anomaly_periods.parquet`

### 18.2 Почему использовались fragment-файлы

Во время extraction данные не писались сразу в финальный parquet, потому что:

- исходные parquet очень большие;
- запись сразу в один конечный файл на каждую скважину/параметр усложняет потоковую сборку;
- требовалась инкрементальная запись по мере прохода по batch-ам.

Использовалась временная схема:

- `raw_wells/<well_id>/_fragments/<param_key>/*.parquet`

После успешного compaction все `_fragments` можно и нужно удалить.

### 18.3 Что считается итоговым хранилищем

Итоговым результатом считаются только файлы вида:

- `salym_prepared/raw_wells/<well_id>/<param_key>.parquet`

Промежуточные `_fragments` не являются частью финального датасета.

## 19. Фактическая политика quality_flag

На текущем этапе в коде реализована следующая логика.

### 19.1 `quality_flag = ok`

Ставится, если:

- в `Value` есть нормальное числовое значение;
- это значение не равно `-9999`;
- это значение не равно `-32768`.

### 19.2 `quality_flag = bad_text`

Ставится, если:

- `ValueText == "Bad"`

В этом случае:

- `value = NULL/NaN`

### 19.3 `quality_flag = sentinel_-9999`

Ставится, если:

- `ValueText == "-9999"`
- или `Value == -9999`
- или из `ValueText` удалось распарсить число `-9999`

В этом случае:

- `value = NULL/NaN`

### 19.4 `quality_flag = sentinel_-32768`

Ставится, если:

- `ValueText == "-32768"`
- или `Value == -32768`
- или из `ValueText` удалось распарсить число `-32768`

В этом случае:

- `value = NULL/NaN`

### 19.5 `quality_flag = text_only`

Ставится, если:

- `Value` отсутствует;
- но `ValueText` удалось распарсить в обычное число;
- и это число не является sentinel.

Пример:

- `Value = NULL`
- `ValueText = "59.6"`

Тогда:

- `value = 59.6`
- `quality_flag = text_only`

### 19.6 `quality_flag = missing_nonphysical`

Ставится, если:

- `Value` отсутствует;
- `ValueText` не равно `Bad`;
- `ValueText` не является sentinel;
- `ValueText` не удаётся интерпретировать как число.

То есть `missing_nonphysical` это общий класс для нечисловых или пустых записей, которые нельзя использовать как физическое измерение.

Важно:

- `missing_nonphysical` это не только про `-9999/-32768`;
- для `-9999` и `-32768` есть отдельные flags;
- `missing_nonphysical` включает случаи вроде:
  - пустого `ValueText`;
  - пустого `Value`;
  - текстовых состояний типа `ON`.

## 20. Наблюдения по фактическим данным

### 20.1 Ряд по годам действительно сшивается

Для ряда скважин подтверждено, что один и тот же параметр идёт непрерывным годовым разрезом `2015 -> 2016 -> 2017 -> 2018`.

Это означает:

- файлы по годам являются разбиением одного и того же канала;
- это не разные показатели под одним именем.

### 20.2 Разные параметры внутри скважины имеют разные временные шкалы

Это не ошибка, а нормальное свойство данных.

Причины:

- разная частота historization;
- возможно change-only поведение источника;
- разные режимы записи каналов.

Следствие:

- на текущем этапе нельзя принудительно приводить все параметры внутри скважины к одной временной сетке.

### 20.3 Нули на текущем этапе не интерпретируются

На текущем этапе:

- нули не удаляются;
- нули не заменяются;
- нули не трактуются автоматически как валидные или невалидные;
- проверка нулей через `Frequency` и физическую логику отложена на следующий этап.

### 20.4 В analog-каналах встречаются текстовые записи

Фактически обнаружен кейс, что даже в каналах, которые по смыслу являются динамическими аналоговыми, встречаются строки вида:

- `value = NULL`
- `value_text = "ON"`

Подтверждённый пример:

- скважина `WS-1403`

Такие записи встречаются одновременно в нескольких динамических каналах:

- `ESP.Frequency`
- `ESP.IntakePressure`
- `ESP.IntakeTemperature`
- `ESP.Motor.CurrentU`
- и других

Это трактуется как:

- текстовое или служебное состояние источника;
- нечисловая запись внутри analog-тега;
- невалидная точка для численного modelling на raw-этапе.

Поэтому на текущем этапе такие записи сохраняются как:

- `value = NULL`
- `value_text = "ON"`
- `quality_flag = missing_nonphysical`

### 20.5 Есть каналы, которые формально присутствуют, но по факту очень плохие

Подтверждённый пример:

- у `US-103` канал `ESP.Motor.Load` в `2016` фактически целиком пустой по численному слою

Это важно:

- наличие файла или тега ещё не гарантирует качественный канал;
- следующий этап обязательно должен учитывать QC, а не только присутствие параметра.

## 21. Ограничения и известные оговорки текущего результата

### 21.1 `excluded_ambiguous_wells.parquet`

Исторически по полному Excel вручную было найдено `11` ambiguous cases.

В текущем результате:

- `excluded_ambiguous_wells.parquet` содержит `8` строк

Рабочее объяснение:

- в итоговый файл попали только те ambiguous wells, которые пересеклись с текущим telemetry-pool и логикой отбора.

Это не считается блокирующей ошибкой текущего raw-этапа, но подлежит отдельной верификации на следующем шаге.

### 21.2 `anomaly_periods.parquet` пока не финальная разметка для модели

Текущая таблица `anomaly_periods.parquet` строится из Excel как event/cycle metadata.

Это значит:

- таблица полезна как эксплуатационный слой;
- но правило формирования настоящих интервалов `от и до` ещё не утверждено окончательно;
- использовать её как production-ready labels без отдельного решения нельзя.

### 21.3 Результат пока не интегрирован в `paano`

Это сознательное ограничение текущего этапа.

На данном этапе:

- собран отдельный raw-контур Salym;
- собраны Excel-based metadata и periods;
- но unified anomaly dataset, ресемплинг и model-ready слой ещё не построены.

## 22. Команды запуска и восстановления

Основные команды:

```bash
./venv/bin/python scripts/salym/build_salym_raw.py --metadata-only
./venv/bin/python scripts/salym/build_salym_raw.py --skip-metadata --skip-anomalies
./venv/bin/python scripts/salym/build_salym_raw.py --skip-metadata --skip-anomalies --skip-extract
```

Назначение:

- `--metadata-only`:
  - строит только metadata и anomaly tables;
- `--skip-metadata --skip-anomalies`:
  - запускает только raw extraction, если metadata уже собраны;
- `--skip-extract`:
  - используется для повторного compaction уже существующих fragment-файлов без повторного extraction.

## 23. Что должен понять новый разработчик, открывший репозиторий

Новый разработчик должен понимать следующие ключевые вещи:

- Salym хранится отдельно от текущего production-контура;
- исходный источник это `120` parquet-файлов и один Excel-реестр;
- обрабатываются только `15` согласованных dynamic-параметров;
- папка = скважина, parquet = параметр;
- у каждого параметра своя временная шкала;
- `value` на raw-этапе не чинится интерполяцией и не приводится к общей сетке;
- `Bad`, `-9999`, `-32768`, `ON` и подобные случаи не превращаются в числа;
- `quality_flag` обязателен для правильной интерпретации канала;
- `anomaly_periods.parquet` пока не финальная production-разметка;
- следующий этап должен заниматься уже не extraction, а QC, логикой интервалов и модельным представлением данных.

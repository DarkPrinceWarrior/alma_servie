# Метод pressure trend для притока

## Контекст

Для класса `pritok` текущий детектор `paano_shared` был дополнен физической
веткой `pressure_trend`. Ветка встроена внутрь существующего detector key
`paano_shared`: отдельный детектор, отдельный отчет и отдельные пользовательские
артефакты не создаются.

Основные файлы остаются прежними:

- `db/pritok_paano_shared_scores.parquet`;
- `db/pritok_paano_shared_predicted_starts.parquet`;
- `artifacts/results/pritok_paano_shared_results.parquet`;
- `artifacts/reports/pritok/pritok_paano_shared_report.html`;
- `artifacts/reports/pritok/pritok_paano_shared_feature_importance.html`.

## Что делает алгоритм

`pressure_trend` оценивает физический тренд давления на приеме насоса для каждой
скважины относительно ее собственной локальной истории. Цель ветки - не заменить
нейросетевой score, а дать ограниченный физический boost, если давление
демонстрирует устойчивое изменение, которое `paano_shared` может увидеть поздно.

Ветка поддерживает оба направления:

- рост давления;
- падение давления.

Это важно, потому что для `pritok` на разных скважинах физический сигнал может
проявляться не одинаково. Например, для `1062` критичным был ранний рост
давления, а для `5144г` - небольшое, но устойчивое падение относительно
локального шума.

## Адаптивные части

Алгоритм не использует правило вида `если давление изменилось на X% за Y дней`.
Вместо этого:

- горизонты анализа строятся адаптивно от длины reference-истории скважины;
- базовая норма считается отдельно для каждой скважины;
- нормализация идет через robust median/MAD, а не через обычные mean/std;
- уровень, изменение, устойчивость и практическая заметность считаются
относительно reference-распределения самой скважины;
- итоговый вклад давления регулируется `pressure_trend_weight`, который
подбирается auto-tune, а не фиксируется вручную под отдельную скважину.

В scores parquet сохраняются диагностические компоненты:

- `paano_score`;
- `paano_tail_score`;
- `pressure_trend_score`;
- `pressure_trend_level`;
- `pressure_trend_change`;
- `pressure_trend_persistence`;
- `pressure_trend_practical`;
- `pressure_trend_direction`;
- `pressure_trend_dominates`.

## Что не является хардкодом под скважины

В коде нет специальных условий для `1062`, `5144г`, `129л`, `3261` или других
конкретных скважин. Также нет условия вида "для этой скважины брать давление
вверх, а для этой вниз".

Физическая ветка работает одинаково для всех скважин `pritok`:

- берет давление на приеме;
- строит адаптивные горизонты;
- считает отклонение от локальной нормы;
- сохраняет физический evidence;
- дает score boost только через общий тюнингуемый вес.

## Где остаются гиперпараметры

Полностью без гиперпараметров такая система невозможна. Важно, что текущие
гиперпараметры являются class-level настройками, а не ручной подгонкой под
отдельные скважины.

Остаются следующие гиперпараметры:

- сетка `pressure_trend_weight`;
- сетка `cooldown_hours`;
- сетка `min_run_points`;
- сетка `gate_mode`;
- operational-лимиты выбора конфига:
  `max_far_per_day`, `max_starts_per_interval`, `max_p90_delay_ratio`;
- формула агрегации physical evidence внутри `pressure_trend`.

Эти параметры задают допустимый operational trade-off: покрытие интервалов,
задержка, число повторных стартов и false alarms.

## Защита от повторных стартов

Для `pritok` отключен обход cooldown после rearm/clear:

```text
bypass_cooldown_after_clear = false
```

Причина: приток часто является длинным трендом, а не одиночным коротким событием.
Если разрешить повторное вооружение сразу после краткой очистки сигнала, одна
длинная аномалия начинает давать десятки стартов. Поэтому для `pritok` cooldown
должен реально ограничивать повторные старты.

## Последний подтвержденный прогон

Последний подтвержденный прогон был выполнен на:

```text
db/pritok_anomaly_database_10min.parquet
detector = paano_shared
```

Финальный выбранный конфиг:

```text
target_far_per_day = 0.25
min_run_points = 4
cooldown_hours = 168
rearm_window_minutes = 30
ema_alpha = 0.12
gate_mode = score_ema
hysteresis_scale = 0.6
bypass_cooldown_after_clear = false
fusion_weight_short = 0.6
pressure_trend_weight = 0.0025
```

Метрики:

```text
all hit_rate = 19/21 = 0.9048
train hit_rate = 18/20 = 0.90
test hit_rate = 1/1 = 1.00
start_count = 60
false_alarms_per_day = 0.0362
avg_starts_per_interval = 2.86
median_abs_delay_hours = 31.5
p90_abs_delay_hours = 110.18
```

Ключевые скважины:

```text
1062   detected 2026-01-02 15:40, delay ~= 1.19 h
5144г  detected 2026-01-27 14:20, delay ~= 16.02 h
902    detected 2025-10-22 01:40, delay ~= 1.67 h
```

Оставшиеся непойманные интервалы:

```text
602 interval 2: 2026-02-20 13:45:45 -> 2026-03-13 00:00:00
691 interval 2: 2026-01-03 00:41:36 -> 2026-01-07 00:00:00
```

## Ограничение честности

Текущий auto-tune подбирает параметры на train-скважинах. Поскольку train сейчас
содержит большую часть размеченных скважин `pritok`, результат нельзя считать
полностью независимой оценкой обобщения на будущие скважины.

Это не ручная подгонка под конкретные скважины, но остается риск переобучения
на текущий набор train wells.

## Следующий шаг для более строгой версии

Чтобы метод был максимально защищен от переобучения, нужно добавить group-CV
или leave-one-well-out tuning:

```text
for each train well:
    exclude this well from tuning
    tune config on other train wells
    evaluate on excluded well

select config that is stable across excluded wells
```

После этого финальный конфиг должен выбираться не по лучшему результату на всех
train-скважинах сразу, а по устойчивости качества при исключении скважин.

Это сделает методологию сильнее для заказчика: будет видно, что физическая
ветка улучшает `pritok` не за счет подгонки под известные скважины, а за счет
обобщаемого pressure-trend evidence.

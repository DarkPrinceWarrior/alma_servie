# План публичного развёртывания alma_servie (MVP)

**Дата:** 15.05.2026
**Статус:** утверждённый MVP-план
**Цель:** выкатить alma_servie в публичный интернет под 5 пользователей с минимально допустимым уровнем защиты. Без сторонних сервисов (Cloudflare, R2, Telegram-боты, observability-стек), всё на собственном железе.

**Что точно решено пользователем:**
- Доменное имя — **`alma-anomaly.ds-mind-lab.ru`** (базовый `ds-mind-lab.ru`, субдомен `alma-anomaly`).
- Cloudflare не используем.
- Сетевик пробросит публичный IP на A100 (порт 443/80).
- Бэкап только локально на этом же сервере, без off-site.
- 5 пользователей, MVP, без 152-ФЗ.
- Без Telegram-алертов, без резервного админа.

---

## 1. Краткий вердикт

В текущем виде в публичный интернет выпускать нельзя. Блокирующих пунктов **5**:

1. `SECRET_KEY = "CHANGE_ME"`, `POSTGRES_PASSWORD = "app"`, `DEBUG=true`, `REFRESH_COOKIE_SECURE=false` — дефолты.
2. TLS не настроен.
3. Postgres слушает `0.0.0.0:5432`, firewall на хосте отсутствует.
4. На бэкенде нет CORS, нет rate-limit, нет CSRF, нет валидации размера загрузки.
5. Production-compose не существует (`backend_roadmap.md` Stage G).

После устранения этих 5 пунктов MVP можно публиковать. Этого достаточно для 5 экспертов.

## 2. Текущее состояние стека (короткая инвентаризация)

| Сервис | Образ | Порт хоста | Healthcheck | Restart |
|--------|-------|------------|-------------|---------|
| backend | python:3.13-slim | 8000 | да | unless-stopped |
| worker | python:3.12-slim, torch 2.11+cu130 | — | нет | unless-stopped, profile `heavy`, GPU id=1 |
| frontend | node:22-alpine | 3000 | нет | unless-stopped |
| postgres | postgres:16 | 5432 | да | unless-stopped |

Тома: `pgdata` (named), `uploads` (named), `../..:/data` (bind rw для worker, ro для backend).
Worker забирает `detection_runs WHERE status='pending'` через `FOR UPDATE SKIP LOCKED` — это уже даёт durability при перезапусках.
Backend стартует через `alembic upgrade head` (Dockerfile, CMD).

Сеть на сервере:
```
0.0.0.0:22    sshd
0.0.0.0:3000  frontend
0.0.0.0:5432  postgres   ← после получения публичного IP — критическая дыра
0.0.0.0:8000  backend
```
UFW отсутствует, iptables — `ACCEPT` везде. Когда коллега пробросит IP → все 4 порта окажутся снаружи. **До этого момента нельзя успеть отстать с firewall и hardening.**

## 3. Архитектурное решение

```
Интернет (TCP 443, 80)
        │
        ▼
  Публичный IP офиса
        │  (NAT port-forward)
        ▼
  A100 server (192.168.101.12)
   ufw: разрешено только 22, 80, 443
        │
        ▼
  Caddy (docker, internal network)
   ├─ ACME HTTP-01 challenge (порт 80)
   ├─ TLS Let's Encrypt автоматически
   ├─ /api/* → backend:8000
   └─ /     → frontend:3000

  backend ──► postgres (только в docker network)
       └──► worker (через таблицу detection_runs)
```

Ключевые отличия от первой версии плана:
- **Нет Cloudflare Tunnel** — сертификат Let's Encrypt выпускается напрямую с сервера через ACME HTTP-01 challenge на порт 80.
- **Лимит 100 МБ снят** — он был только из-за Cloudflare. Теперь технический потолок — что выставим в Caddy (поставим 500 МБ как разумный максимум).
- **Нет встроенной DDoS-защиты.** Если кто-то начнёт спамить — единственная защита это slowapi rate-limit в бэкенде + ufw на хосте. Для 5 экспертов и тихой работы — приемлемо. Риск зафиксирован в реестре.

## 4. Этапы развёртывания

### Этап 0. Предусловия (от вас и коллеги)

1. Сетевик пробросил публичный IP на A100, порты 80 и 443 открыты, порты 22/5432/3000/8000 наружу не пробрасываются.
2. Доменное имя уточнено. A-запись `alma-anomaly.ds-mind-lab.ru` → публичный IP.
3. Сгенерирован SSH-ключ для деплоя из GitHub Actions (опционально, для CI на P2 этапе).

Без п. 1 и 2 двигаться нельзя.

### Этап 1. Hardening конфигурации (~0.5 дня)

Файлы: `app/back/.env.example`, `app/back/src/back/core/config.py`.

1. Сгенерировать секреты:
   ```bash
   openssl rand -hex 64        # SECRET_KEY (≥64 байт)
   openssl rand -base64 32     # POSTGRES_PASSWORD
   openssl rand -base64 32     # ADMIN_PASSWORD (первый запуск)
   ```
2. В `config.py` добавить валидатор — отказ от старта при дефолтных значениях:
   ```python
   @field_validator("secret_key")
   @classmethod
   def _no_default_secret(cls, v: str) -> str:
       if v in {"CHANGE_ME", "", None}:
           raise ValueError("SECRET_KEY должен быть выставлен явно")
       return v
   ```
3. Дефолты на production-безопасные:
   - `DEBUG = False`.
   - `REFRESH_COOKIE_SECURE = True` если `ENVIRONMENT == "production"`.
   - `POSTGRES_HOST = "postgres"` (имя контейнера).
4. Обязательные env-vars: `SECRET_KEY`, `POSTGRES_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `DATABASE_URL`, `ENVIRONMENT=production`, `REFRESH_COOKIE_SECURE=true`, `CORS_ORIGINS=https://alma-anomaly.ds-mind-lab.ru`, `PUBLIC_BASE_URL=https://alma-anomaly.ds-mind-lab.ru`.
5. **SOPS + age для секретов в git:**
   ```bash
   age-keygen -o ~/.config/sops/age/alma_servie.txt
   export SOPS_AGE_RECIPIENTS=$(awk '/public key:/{print $4}' ~/.config/sops/age/alma_servie.txt)
   sops --encrypt --age "$SOPS_AGE_RECIPIENTS" .env > .env.enc
   ```
   `.env.enc` коммитим, `.env` в `.gitignore`. На сервере приватный ключ в `/root/.config/sops/age/keys.txt` с `chmod 600`. Декрипт перед `docker compose up`: `sops --decrypt .env.enc > .env`.

**Verify:** backend падает на старте без `SECRET_KEY`. Юнит-тест на валидатор.

### Этап 2. Firewall на хосте (~0.5 часа)

На A100 включить UFW:
```bash
ssh a100-remote 'apt-get install -y ufw && \
  ufw default deny incoming && \
  ufw default allow outgoing && \
  ufw allow 22/tcp && \
  ufw allow 80/tcp && \
  ufw allow 443/tcp && \
  ufw allow from 192.168.101.0/24 && \
  ufw allow from 10.10.40.0/24 && \
  ufw --force enable && \
  ufw status verbose'
```
Локальная LAN (`192.168.101.0/24`) и VLAN (`10.10.40.0/24`) остаются доступны полностью — это безопасно, они физически за NAT офиса.

`fail2ban` для SSH-брутфорса (опционально, рекомендую):
```bash
apt-get install -y fail2ban
# дефолтный jail.conf уже защищает sshd через 5 попыток / 10 мин блок
systemctl enable --now fail2ban
```

### Этап 3. Production-compose (~1 день)

Файл: `app/back/compose.prod.yaml` (overlay поверх `compose.yaml`).

1. Снять `ports:` с postgres, backend, frontend — наружу никто из них не светится:
   ```yaml
   services:
     postgres:
       ports: !reset []
     backend:
       ports: !reset []
     frontend:
       ports: !reset []
   ```
2. Добавить сервис `caddy` с автоматическим Let's Encrypt:
   ```yaml
   caddy:
     image: caddy:2.10
     restart: unless-stopped
     ports:
       - "80:80"
       - "443:443"
     volumes:
       - ./Caddyfile:/etc/caddy/Caddyfile:ro
       - caddy_data:/data
       - caddy_config:/config
     environment:
       ACME_EMAIL: ${ACME_EMAIL}     # ваш email для Let's Encrypt
   ```
3. Hardening для backend/frontend/worker:
   ```yaml
   read_only: true
   tmpfs: [/tmp, /var/run]
   security_opt: ["no-new-privileges:true"]
   cap_drop: [ALL]
   ulimits: { nofile: 65535, nproc: 4096 }
   ```
4. Healthcheck `worker`:
   ```yaml
   healthcheck:
     test: ["CMD-SHELL", "pgrep -f 'back.worker.loop' >/dev/null"]
     interval: 30s
     timeout: 5s
     retries: 3
   ```
5. Healthcheck `frontend`:
   ```yaml
   healthcheck:
     test: ["CMD", "wget", "--spider", "-q", "http://127.0.0.1:3000/"]
     interval: 30s
     timeout: 5s
     retries: 3
   ```
6. Pin образов: `image: backend:${IMAGE_TAG:-latest}` — `:latest` оставляем только локально, для прода CI выставляет `IMAGE_TAG=<git-sha>`.

**Caddyfile:**
```
alma-anomaly.ds-mind-lab.ru {
    encode gzip
    request_body { max_size 500MB }

    handle /api/* {
        reverse_proxy backend:8000 {
            header_up X-Real-IP {http.request.remote.host}
            header_up X-Forwarded-For {http.request.remote.host}
            header_up X-Forwarded-Proto {http.request.scheme}
        }
    }

    handle {
        reverse_proxy frontend:3000
    }
}
```
Caddy сам зарегистрирует Let's Encrypt-сертификат на старте (HTTP-01 challenge через порт 80) и будет автоматически перевыпускать.

**Verify:**
- На сервере: `ss -tlnp` показывает наружу только sshd, caddy 80, caddy 443.
- С внешнего компьютера: `curl -I https://alma-anomaly.ds-mind-lab.ru` — `HTTP/2 200`.
- `curl https://alma-anomaly.ds-mind-lab.ru:5432` — не отвечает (порт за UFW).
- Сертификат от Let's Encrypt валиден (Chrome не ругается).

### Этап 4. Hardening бэкенда (~1 день)

Файлы: `app/back/src/back/main.py`, новые middleware.

1. **CORS allow-list:**
   ```python
   app.add_middleware(
       CORSMiddleware,
       allow_origins=settings.cors_origins,   # ["https://alma-anomaly.ds-mind-lab.ru"]
       allow_credentials=True,
       allow_methods=["GET","POST","PUT","PATCH","DELETE","OPTIONS"],
       allow_headers=["Authorization","Content-Type","X-CSRF-Token"],
   )
   ```
2. **CSRF double-submit token:**
   - При логине бэкенд ставит non-HttpOnly cookie `csrf_token=<random>` со сроком как у refresh.
   - Front копирует значение в заголовок `X-CSRF-Token` на каждый мутирующий запрос.
   - Middleware сравнивает cookie и заголовок — на mismatch 403.
3. **Rate-limit (slowapi):**
   - `/api/auth/login` — 5/мин/IP.
   - `/api/auth/refresh` — 30/мин/IP.
   - `/api/uploads` POST — 10/мин/IP.
   - `/api/detections` POST — 30/мин/IP.

   Key — клиентский IP из `X-Forwarded-For` (Caddy его прокидывает).
4. **Cookie hardening:** `Secure=True`, `SameSite=Lax`, `Domain=alma-anomaly.ds-mind-lab.ru`, `Path=/api/auth/refresh`.
5. **Trusted proxies:** uvicorn запускать с `--forwarded-allow-ips=*` (Caddy и backend в одной docker network, `*` тут безопасно).
6. **Валидация загрузки:**
   - `Content-Length` ≤ 500 МБ (лимит Caddy).
   - Magic-проверка: первые 4 байта = `PK\x03\x04` (ZIP-сигнатура xlsx).
   - Имя файла на диске — слаг от run_id, оригинальное имя не сохраняем.
7. **ClamAV на MVP — не ставим.** 5 экспертов из доверенной компании, антивирусная проверка xlsx преждевременна. Добавим, если заказчик расширится. Риск зафиксирован.

**Verify:** curl с поддельным CSRF → 403; 6-й логин подряд → 429; xlsx с фальшивым content-type → 422.

### Этап 5. Локальный бэкап Postgres (~0.5 часа)

Простой `pg_dump` cron, всё на этом же сервере. **Не защищает от потери сервера**, но защищает от логических ошибок (случайный DROP, кривая миграция).

1. Папка `/var/backups/alma_servie/` на сервере (отдельный путь от volumes Postgres).
2. Cron на хосте:
   ```cron
   30 2 * * * docker compose -f /root/projects/alma_servie/app/back/compose.yaml -f compose.prod.yaml \
     exec -T postgres pg_dump -U app alma_servie | gzip > \
     /var/backups/alma_servie/alma_$(date +\%Y\%m\%d).sql.gz
   0 3 * * * find /var/backups/alma_servie/ -name 'alma_*.sql.gz' -mtime +14 -delete
   ```
3. Ротация: храним 14 дней.
4. Размер дампа — мегабайты (БД содержит только metadata: пользователи, detection_runs). Парквет-результаты лежат отдельно в volume `uploads`.

**Restore drill — раз в месяц вручную:**
```bash
gunzip < /var/backups/alma_servie/alma_<date>.sql.gz | \
  docker compose exec -T postgres psql -U app -d alma_servie_restore_test
```
Запустить руками раз, убедиться что данные читаются. Записать в `docs/runbook_restore.md`.

**Опциональное расширение позже:** rsync `/var/backups/` на USB-диск раз в неделю — это даёт off-site (диск дома). Стоит $30 за внешний SSD, делается за 10 минут. **Сильно рекомендую** даже для MVP.

### Этап 6. TTL загрузок (~0.5 часа)

Том `uploads` сейчас бесконечно растёт. Простая cron-стрижка:

1. Контейнер `ofelia` либо хост-cron:
   ```cron
   0 4 * * * find /var/lib/docker/volumes/alma_servie_uploads/_data/excel -mtime +30 -delete
   0 4 * * * find /var/lib/docker/volumes/alma_servie_uploads/_data/results -mtime +90 -type d -exec rm -rf {} +
   ```
2. После очистки на стороне ФС — пометить соответствующие `detection_runs.archived_at = now()` через `back.cli` (опционально на MVP — можно делать руками).
3. Pre-flight на бэкенде: если том `uploads` >95% — возвращать 507. Реализация: периодический check через `os.statvfs("/uploads")` в healthcheck.

### Этап 7. Выкатка и smoke-тест (~0.5 часа)

```bash
# на сервере
cd /root/projects/alma_servie/app/back
sops --decrypt .env.enc > .env
docker compose -f compose.yaml -f compose.prod.yaml --profile heavy up -d
docker compose ps
docker compose logs -f caddy   # ждём `certificate obtained`
```

Smoke-сценарий:
1. С внешнего компа открыть `https://alma-anomaly.ds-mind-lab.ru` → редирект на /login.
2. Войти под admin → главная → загрузить тестовый xlsx → дождаться 3/3 → результат отображается.
3. Открыть `https://alma-anomaly.ds-mind-lab.ru:5432` — должно фейлить (порт за UFW).
4. Открыть `http://alma-anomaly.ds-mind-lab.ru` — Caddy редиректит на HTTPS.
5. SSL Labs (`https://www.ssllabs.com/ssltest/analyze.html?d=alma-anomaly.ds-mind-lab.ru`) — оценка A.

## 5. Что отложено на потом (P2)

Эти пункты не нужны для MVP с 5 пользователями, но фиксируем для будущего:

| Пункт | Когда вернуться |
|-------|-----------------|
| Off-site бэкап (USB / второй сервер) | при росте критичности данных |
| ClamAV-sidecar для xlsx | при росте до >10 пользователей или внешних клиентов |
| CI/CD через GHCR + docker rollout + GitHub Actions | когда команда станет >2 человек |
| Observability (Loki/Grafana) | когда производственные инциденты начнут случаться чаще раза в месяц |
| pgBackRest + WAL-archiving | при росте БД и появлении требования RPO < 24 ч |
| Worker drain pattern для GPU-rollout | когда обновления станут чаще и есть риск потери задания при рестарте |
| Cloudflare Tunnel / WAF / DDoS | при появлении публичного интереса/атак |

Пока работаем без них — для MVP это разумный trade-off.

## 7. Реестр рисков

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Утеря сервера (пожар/кража/ssd dead) → потеря всех данных | низкая | критическое | **Open:** off-site хотя бы USB-диск (см. Этап 5, опциональное расширение) |
| DDoS на публичный IP | низкая | средняя | На MVP — терпим, ufw + slowapi. При появлении проблем → Cloudflare Tunnel включается за час |
| Брутфорс логина | средняя | средняя | slowapi 5/мин + fail2ban-jail на nginx-access лог Caddy (можно добавить позже) |
| GPU OOM при параллельных загрузках | низкая | средняя | Worker строго 1 in-flight; slowapi на `/api/uploads` |
| Том uploads растёт без контроля | высокая | средняя | TTL-cron в Этапе 6, healthcheck-507 при >95% |
| Падение Postgres из-за кривой миграции | средняя | средняя | pg_dump-бэкапы из Этапа 5, restore drill |
| Эксплойт через xlsx-парсер | низкая | высокая | На MVP без ClamAV принимаем. При расширении — sidecar (P2) |
| Утечка `.env.enc` (компрометация age-ключа) | низкая | высокая | Age-ключ только на сервере, `chmod 600`, ротация раз в полгода |
| Сертификат Let's Encrypt не продлевается | низкая | средняя | Caddy продлевает автоматически. Healthcheck-алерт на истечение (P2) |

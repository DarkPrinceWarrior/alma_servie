# План публичного развёртывания alma_servie

**Дата:** 15.05.2026
**Статус:** черновик плана, готов к утверждению
**Цель:** сделать веб-приложение alma_servie доступным из публичного интернета с любой точки мира при следующих гарантиях:

- модель и инференс работают стабильно на GPU 1× A100;
- данные сохранно хранятся и резервируются;
- сервер за NAT остаётся защищён, ни одного публичного порта на A100 наружу не открыто;
- работа команды продолжается через стандартный workflow «git push → автоматический деплой».

## 1. Краткий вердикт по готовности

Стек собран и работает локально, но в текущем виде в публичный интернет выпускать **нельзя**. Блокирующих пунктов **7**:

1. Сервер за NAT, публичного IPv4 нет — нужен туннель.
2. TLS не настроен.
3. `SECRET_KEY = "CHANGE_ME"`, `POSTGRES_PASSWORD = "app"`, `DEBUG=true` в дефолтах.
4. Postgres слушает `0.0.0.0:5432` без firewall — критическая дыра.
5. CORS, CSRF, rate-limit на бэкенде не реализованы.
6. Бэкапов Postgres нет; том `uploads` без лимита, без TTL, без антивирусной проверки.
7. Production-варианта compose-файла нет (`app/back/docs/backend_roadmap.md`, Stage G, фиксирует это как открытую задачу).

После устранения этих 7 пунктов и закрытия системы на список приглашённых пользователей её можно публиковать.

## 3. Архитектурное решение

Сервер за NAT, без публичного IPv4 — это определяет всю верхнюю часть стека.

### 3.1 Публичная экспозиция — Cloudflare Tunnel

`cloudflared` ставится контейнером рядом со стеком, делает **исходящее** TCP-подключение к ближайшему дата-центру Cloudflare и публикует выбранный hostname (`alma.<домен>`) c автоматическим TLS на edge. На стороне A100 никаких входящих портов открывать не нужно, NAT-роутер не трогаем.

Почему не альтернативы:
- **Tailscale Funnel** — только порты 443/8443/10000 и `*.ts.net`, нельзя свой домен.
- **ngrok платный** — vendor lock-in, дороже без выигрыша.
- **VPS + WireGuard + Caddy на VPS** — больше работы, лишний хост для патчей, SPOF.
- **frp** / `ssh -R` — всё равно требует VPS; если он есть, проще Caddy на нём, чем разворачивать `frp`.

**Известное ограничение и митигация:** Free/Pro план Cloudflare режет тело загрузки на 100 МБ (Business — 200 МБ; снять можно только на Enterprise). Excel-выгрузки с месячной телеметрией могут превышать порог. Решение: для эндпоинта `/api/uploads` выделить отдельный домен `upload.<домен>`, который идёт через Tailscale Funnel или WireGuard на маленький VPS. Альтернатива — клиентский chunked-upload порциями <100 МБ. Текущий тестовый `.xlsx` весит 5.4 МБ — на начальном этапе можно пожить с одним каналом и поднимать второй по необходимости.

### 3.2 Reverse-proxy — Caddy

Caddy внутри стека терминирует HTTP на стороне Docker network, маршрутизирует `/api/*` → `backend:8000`, всё остальное → `frontend:3000`. Внешний TLS даёт Cloudflare; `cloudflared` подключается к `caddy:80`. Никаких ACME-челленджей на сервере не нужно — это сильно упрощает Caddyfile.

Почему не Traefik/Nginx: у нас 3 фиксированных сервиса, dynamic discovery не нужен (Traefik избыточен), nginx требует ручного certbot (а нам сертификат и не нужен на origin).

### 3.3 Очередь заданий — Postgres

Worker уже забирает задания строкой `detection_runs WHERE status='pending' FOR UPDATE SKIP LOCKED`. Это даёт durability — при перезапуске worker задания не теряются, при rollout можно дренировать. Менять ничего не нужно, фиксируем как архитектурный инвариант.

### Этап 3. Hardening бэкенда (~1 день)

Файлы: `app/back/src/back/main.py`, новые middleware.

1. **CORS allow-list:**
   ```python
   app.add_middleware(
       CORSMiddleware,
       allow_origins=settings.cors_origins,    # ["https://alma.<домен>"]
       allow_credentials=True,
       allow_methods=["GET", "POST", "DELETE", "PUT", "PATCH", "OPTIONS"],
       allow_headers=["Authorization", "Content-Type", "X-CSRF-Token"],
   )
   ```
2. **CSRF double-submit token:**
   - При логине бэкенд ставит non-HttpOnly cookie `csrf_token=<random>`; срок жизни = срок refresh.
   - Front копирует значение из cookie в заголовок `X-CSRF-Token` на каждый POST/PUT/PATCH/DELETE.
   - Middleware сравнивает cookie и заголовок; на mismatch — 403.
   - `/api/auth/refresh` использует тот же механизм.
3. **Rate-limit (slowapi):**
   ```python
   limiter = Limiter(key_func=lambda req: req.headers.get("CF-Connecting-IP") or req.client.host)
   ```
   Лимиты:
   - `/api/auth/login` — 5/мин/IP.
   - `/api/auth/refresh` — 30/мин/IP.
   - `/api/uploads` POST — 10/мин/IP.
   - `/api/detections` POST — 30/мин/IP.

   На Cloudflare WAF — дублирующее правило по логину (5/мин, блок 10 мин при 401/403 спаме) как defense in depth.
4. **Cookie hardening:** `Secure=True`, `SameSite=Lax`, `Domain=alma.<домен>` (явно), `Path=/api/auth/refresh` сохраняем. `Strict` не берём — ломает приход по внешним ссылкам без выигрыша при POST-only refresh.
5. **Trusted proxies:** `uvicorn` запускать с `--forwarded-allow-ips="*"` либо явным списком IP Cloudflare. Иначе rate-limit и логи видят IP туннеля, а не клиента.
6. **Валидация загрузки:**
   - `Content-Length` ≤ 100 МБ (или больше через upload-сайдченнел).
   - `magic`-проверка: первые 4 байта = `PK\x03\x04` (ZIP-сигнатура `.xlsx`).
   - Имя файла — слаг, без сохранения оригинального имени на диске.
7. **ClamAV sidecar:**
   ```yaml
   clamav:
     image: clamav/clamav:1.4
     volumes: [clamav_db:/var/lib/clamav]
   ```
   Бэкенд через `python-clamd` пингует `tcp://clamav:3310` перед парсингом xlsx. На FOUND — 422, запись в `audit_log`, файл в карантин. `xlsx` — это zip-with-XML и известный носитель VBA-malware.

**Verify:** curl с поддельным CSRF → 403; 6-й логин подряд → 429; xlsx с EICAR-сигнатурой → 422; xlsx >100 МБ → 413.

### Этап 5. Бэкап Postgres (~0.5 дня)

**Инструмент — pgBackRest** (daily full + WAL archiving + сжатие + параллельный restore). pg_dump — простой fallback, но WAL-archiving из коробки даёт PITR и почти-нулевой RPO; ради 10 ГБ Postgres ставить это однажды дешевле, чем потом восстанавливать с резкой потерей данных.

1. Контейнер `pgbackrest`:
   ```yaml
   pgbackrest:
     image: pgbackrest/pgbackrest:latest
     volumes:
       - pgdata:/var/lib/postgresql/data:ro
       - pgbackrest_repo:/var/lib/pgbackrest
       - ./pgbackrest.conf:/etc/pgbackrest/pgbackrest.conf:ro
     command: ["sleep", "infinity"]
   ```
2. Postgres настроить на WAL-archiving в `postgresql.conf` (через `command:` параметры):
   ```
   archive_mode = on
   archive_command = 'pgbackrest --stanza=alma archive-push %p'
   max_wal_senders = 3
   wal_level = replica
   ```
3. Расписание (host cron на сервере):
   ```cron
   0 2 * * 0   docker compose exec -T pgbackrest pgbackrest --stanza=alma --type=full backup
   0 2 * * 1-6 docker compose exec -T pgbackrest pgbackrest --stanza=alma --type=diff backup
   */15 * * * * docker compose exec -T pgbackrest pgbackrest --stanza=alma archive-push
   ```
4. **Off-site:** rclone-контейнер ежедневно льёт `/var/lib/pgbackrest` на Cloudflare R2 (zero egress, $0.015/ГБ·мес, 10 ГБ бесплатно) либо Hetzner Storage Box. Шифрование на стороне rclone (AES256).
5. **Restore drill** — каждые 30 дней автоматически:
   - GitHub Actions запускает `pgbackrest restore --stanza=alma --type=time --target='1 hour ago'` в одноразовый compose-проект.
   - Smoke-запросы: `SELECT count(*) FROM users`, `SELECT count(*) FROM detection_runs WHERE created_at > now() - interval '7 days'`.
   - Падение шлёт алерт в Telegram.

Непротестированный бэкап = отсутствующий бэкап.

**Verify:** один цикл backup → имитация потери данных → restore → данные на месте.

### Этап 6. Lifecycle загрузок (~0.5 дня)

1. **TTL cron** (контейнер `ofelia` либо `tini`-based sidecar):
   - `find /uploads/excel -mtime +30 -delete`
   - `find /uploads/results -mtime +90 -type d -exec rm -rf {} +`
   - Удалённые `run_id` помечаются в БД `detection_runs.archived_at = now()` через бэкенд CLI.
2. **Жёсткий лимит:** 50 ГБ на том `uploads`. Скрипт-pruner усекает с самых старых, пока не уложится. Каждое усечение логируется + Telegram-алерт при >80%.
3. **Pre-flight на бэкенде:** 507 «недостаточно места», если том >95%.
4. **Опционально (на этапе роста):** Cloudflare R2 для cold-storage с presigned-URL. Фронт грузит напрямую в bucket, обходя 100 МБ лимит туннеля. До этого — не нужно.

### Этап 8. CI/CD (~1 день)

1. **Registry:** GHCR. Каждый сервис — отдельный image (`ghcr.io/darkprincewarrior/alma-backend:<sha>`, `-worker`, `-frontend`).
2. **GitHub Actions** `.github/workflows/build-deploy.yaml`:
   - Trigger: push в `main` (production) и в `app/webapp` (staging).
   - Шаги:
     1. Build matrix — backend, worker, frontend — `docker/build-push-action@v6` c buildx cache.
     2. **Trivy scan** обязательный: `--severity CRITICAL,HIGH --ignore-unfixed`, fail при находках.
     3. Push в GHCR с тегами `<sha>` и `production` / `staging`.
     4. Деплой по SSH: `DOCKER_HOST=ssh://a100-remote docker compose pull && docker rollout backend frontend` — zero-downtime для stateless сервисов.
     5. **Worker drain pattern** (отдельный шаг):
        - `docker compose exec backend python -m back.cli worker_drain` — флаг `worker_state='draining'` в БД.
        - Backend перестаёт класть новые `pending`.
        - Опрос: `SELECT count(*) FROM detection_runs WHERE status IN ('pending','running')` до 0 (timeout 5 мин).
        - `docker compose up -d worker` — пересоздать.
        - Сбросить флаг `worker_state='active'`.

   Одна A100 = один worker в моменте, поэтому rolling update без drain невозможен. С 5–30 с на инференс drain укладывается в <1 мин.
3. **Rollback:** `git revert` + push, либо тег `production-<prev_sha>` в GHCR.

### Этап 9. Открытые архитектурные пункты (фоном)

1. **Multi-tenant?** Сейчас RBAC = {user, admin}, все видят всё. Если будут разные клиенты — добавить `org_id` и фильтры.
2. **Audit log.** Любое мутирующее API → запись в `audit_log` (кто/когда/что). Для индустриального заказчика нужен по compliance.
3. **`/etc/gai.conf` IPv4-precedence** на сервере (`CLAUDE.md`) — не трогать.
4. **Postgres-как-очередь** — устраивает на 10 пользователей и <100 заданий/час. Поднимется лимит — Redis Streams / RabbitMQ.

## 6. Реестр рисков

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Cloudflare 100 МБ лимит блокирует загрузку | средняя | средняя | Tailscale-sidechannel либо chunked-upload |
| Worker «зависает» на одной задаче, очередь блокируется | низкая | высокая | timeout на subprocess, healthcheck, alert на длину очереди |
| Утечка `.env.enc` (компрометация age-ключа) | низкая | высокая | age-ключ только на сервере и в CI secret, ротация раз в 6 мес |
| GPU OOM при параллельных загрузках | средняя | средняя | Worker strict 1 in-flight; rate-limit на `/api/uploads` |
| Том `uploads` растёт без контроля | высокая | средняя | TTL-cron (Этап 6), агрегированный отчёт раз в неделю |
| Cloudflare блокирует домен (false-positive abuse-engine) | низкая | высокая | заранее сконфигурированный VPS+WireGuard как fallback |
| Подпись миграций в чужой ветке вызывает рассинхронизацию | низкая | высокая | `alembic upgrade head` в Dockerfile + ревью PR |
